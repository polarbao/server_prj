# 项目分析、VSCode 迁移与 Go 语言改造可行性报告

> [!NOTE]
> 本报告定义了项目从 Visual Studio 迁移到 VSCode 的技术路线，并确立了“短期补足功能并迁移 VSCode，长期平滑向 Go 语言演进”的双阶段路线图。

---

## 一、 项目现状与业务分析

### 1.1 项目性质与功能定位
`hard2Ser`（本地中控网关）作为边缘设备中枢，承担以下核心职责：
- **云端服务通信**：通过基于 `libhv` 封装的 `WSClient` 建立 WebSocket 长连接，双向同步状态及业务任务。
- **本地硬件控制（Work/Device 层）**：调度扫码设备（`ScanWork`）、手动控制终端（`ManuWork`）、自动贴标机（`StickWork`）。
- **本地网络与图像采集（IPC 层）**：通过 `CameraTcpMgr` 获取本地工业相机图片，并管理本地 TCP/UDP 传输。
- **云存储集成**：集成了阿里云 OSS SDK（`aliCloudOss`）上传图片和文件。
- **用户界面（UI 层）**：基于 Qt 5.15 Widgets 构建的本地监控界面。

### 1.2 开发阶段诊断
- **过渡期**：目录名是 `hard2Ser_3_0`，但内部大量使用 `hard2Ser_2_0` 相关的类和文件名，正处于重构和目录升级过渡期。
- **构建强依赖**：项目目前完全绑定在 Windows 下的 MSBuild（Visual Studio 解决方案）以及 Qt VS Tools 插件上，无法跨平台构建。

## 二、 双阶段重构与演进路线图 (Short-Term & Long-Term Roadmap) [NEW]

为了确保项目的平稳重构与最终向 Go 语言平滑迁移，我们制定了双阶段开发策略：

```
+---------------------------------------------------------------------------------+
|                     【短期计划】 补足 C++ 功能，迁移至 VSCode                    |
| 1. 用 CMake+vcpkg+MSVC 重建构建系统，全面替代 VS (.sln) 依赖。                    |
| 2. 补足 SQLite 数据库、TCP/UDP 全协议抽象、自愈看门狗、离线缓存同步等 7 大核心模块。|
| 3. 面向 Go 重写预留接口：将业务逻辑层与 Qt UI 彻底剥离，设计通用的 JSON-IPC 通道。|
+----------------------------------------+----------------------------------------+
                                         | 核心逻辑稳定，IPC 接口就绪
                                         v
+---------------------------------------------------------------------------------+
|                     【长期计划】 业务后台重写为 Go，UI 综合升级                   |
| 1. 用 Go 语言完全重写业务层（多线程调度）、数据层（SQLite）及通信层（全协议）。   |
| 2. 方案 A（复用 Qt）：原 C++ Qt UI 通过 Local IPC 通道连接 Go 编写的后台进程。     |
| 3. 方案 B（纯 Go 桌面）：将 UI 迁移至 Wails 框架，使用 Vue/React 重写，彻底淘汰 C++。|

```

## 三、 从 VS 迁移到 VSCode 的改造工作指南（短期计划）

VS 依靠 `.vcxproj` 进行隐式编译。要迁移至 VSCode 开发，必须转换为现代化的 CMake 构建系统。

### 3.1 引入 CMake 构建系统
在根目录下新建 `CMakeLists.txt`，利用 `AUTOMOC/AUTOUIC/AUTORCC` 自动处理 Qt 的元对象和界面文件编译，并链接 `3rdParty` 库。

### 3.2 VSCode 配置文件 (.vscode/)
配置 `c_cpp_properties.json` 指定 C++20 标准和编译器路径；配置 `launch.json` 并添加动态库（DLL）路径至环境变量中。

## 四、 C++ 更改为 Go 语言开发的可行性与接口预留设计（长期计划）

在短期 C++ 改造中，必须预先考虑长期 Go 语言的替换。

### 4.1 核心设计：局部进程间通信接口预留 (IPC Boundaries)
为了让以后的 Go 语言能平滑替代 C++ 后台，短期内我们在 UI 层和业务层之间预留**局域网/本地进程间通信 (Local IPC) 边界**：
- **设计原理**：C++ UI 层不直接硬编码调用业务类（如 `WorkThdMgr`），而是通过统一的本地套接字（Local WebSocket 或 TCP）与业务层进行消息传递。
- **协议格式**：数据传输采用标准的 **JSON** 格式，避免使用 C++ 特有的二进制结构体。

```
【长期迁移时的进程拓扑图】
+-----------------------+              Local IPC (JSON)             +-----------------------+
|  C++ Qt UI 进程       | <=======================================> |  Go 业务后台进程        |
|  (仅负责界面渲染与事件)  |          (WebSocket / TCP @ Port 127.0.0.1) |  (完全替换原有 C++ 后台) |
+-----------------------+                                           +-----------------------+
```

### 4.2 长期 UI 的技术升级评估
当 C++ 业务层完全迁移至 Go 后，UI 层的升级路线有两种选择：

#### 方案 A：保留现有的 Qt GUI 
- *实现*：将 Qt UI 编译为独立的前台 EXE，通过本地 WebSocket 与 Go 编写的网关后台通信。
- *优点*：最大化保留现有的 C++ Qt UI 资产，零改动前端。
- *缺点*：部署时需要分发两个 EXE，且 C++ 编译环境仍需保留。

#### 方案 B：全面重构为 Wails 桌面端（推荐）
- *实现*：采用 **Wails** 框架，前端使用 HTML5 / Vue 3 构建，Go 作为后台逻辑，无缝编译为单个打包好的 EXE。
- *优点*：彻底摆脱 C++ 编译器和 Qt 环境；界面动效和现代美化上限极高，更契合现代 Web 桌面应用开发。
- *缺点*：需要前端人员重写 UI 页面。
